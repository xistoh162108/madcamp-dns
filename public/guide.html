DevFest 2026 배포 가이드

DNS 서비스에서 우리 팀 주소를 만들고, Dokploy에 앱을 올려서 https://team1.gdgoc-devfest.org 같은 주소로 공개하는 전 과정을 정리했습니다. 예시의 team1은 각자 팀 ID로 바꿔 읽어 주세요.

PC 전용

이 가이드는 휴대폰에서도 볼 수 있지만, DNS 서비스 관리 화면(dns.gdgoc-devfest.org)은 PC 브라우저에서만 열립니다. 휴대폰으로 접속하면 "PC에서 접속해 주세요" 안내만 나옵니다. Dokploy는 휴대폰에서도 열리긴 하지만 화면이 좁아 설정하기 어려우니 PC로 작업하는 것을 권장합니다.

요청이 우리 앱까지 가는 길은 아래와 같습니다. DNS 서비스는 1번(주소 → 서버 연결)만 담당하고, 실제 앱 실행과 HTTPS 인증서는 Dokploy가 맡습니다.

  1. 브라우저가 team1.gdgoc-devfest.org의 위치를 물으면, DNS 서비스에서 만든 레코드가 "공용 서버(vps.gdgoc-devfest.org)로 가라"고 답합니다.
  2. 브라우저가 공용 서버의 443 포트로 접속합니다. 모든 팀이 같은 서버, 같은 포트를 씁니다.
  3. 서버 앞단의 Traefik이 주소(Host)를 보고, Dokploy Domains에 그 주소를 등록한 팀 앱으로 요청을 넘깁니다.

DNS 서비스는 Dokploy 전용이 아닙니다. 우리 팀 주소는 공용 서버(Dokploy)뿐 아니라 팀원이 따로 쓰는 개인 VM, 클라우드 서버, Vercel 같은 외부 호스팅, 터널을 연 노트북 어디에도 붙일 수 있습니다(어디로 연결할까). 아래는 가장 많이 쓰는 Dokploy 기준 설명입니다.

Dokploy에 올릴 때는 주소 하나를 공개하려면 두 곳에 같은 주소를 적어야 합니다. DNS 서비스의 레코드(1번)와 Dokploy의 Domains(3번)입니다. 둘 중 하나라도 빠지면 접속되지 않습니다.

공용 자원

16GB를 모든 팀이 나눠 쓰기 때문에 한 팀이 메모리를 많이 쓰면 다른 팀 앱이 느려지거나 꺼질 수 있습니다. 팀당 1GB 안팎을 목표로 잡아 주세요.

  • 개발 서버(npm run dev, next dev, vite, flask run --debug)로 띄우지 말고, 빌드한 결과를 실행하세요. 개발 서버는 메모리를 몇 배 더 씁니다.
  • 빌드는 메모리를 가장 많이 쓰는 순간입니다. 여러 앱을 동시에 Deploy하지 말고 하나씩 배포하세요.
  • 안 쓰는 Application과 Compose는 Stop하거나 지워 주세요.
  • 각 앱의 CPU·메모리 사용량은 Dokploy의 Monitoring 탭에서 볼 수 있습니다.

배포 순서 요약

  1. DNS 서비스에 로그인해서 팀 주소를 확인합니다.
  2. 레코드 추가에서 @ → CNAME → vps.gdgoc-devfest.org를 만듭니다. proxy는 끈 채로 둡니다.
  3. Dokploy에 로그인하고 팀 프로젝트를 엽니다.
  4. 코드를 GitHub에 올리고, Application을 만들어 저장소와 빌드 방식을 지정합니다.
  5. 환경 변수를 넣고 Deploy합니다. Logs에서 앱이 떴는지 봅니다.
  6. Domains에 같은 주소를 넣고 HTTPS를 켠 뒤 한 번 더 Deploy합니다.
  7. 브라우저에서 https://team1.gdgoc-devfest.org를 열어 확인합니다.

Vercel, Netlify 같은 외부 호스팅이나 공인 IP가 있는 개인 VM을 쓴다면 2번에서 값만 바꾸고 3~6번은 건너뜁니다(어디로 연결할까, 개인 VM에 붙이기). 내 노트북이나 공인 IP가 없는 VM에서 띄운 서버를 공개하려면 터널을 씁니다.

DNS 서비스: 레코드 추가

레코드는 "이 주소는 저기로 가라"는 한 줄짜리 규칙입니다. Dokploy에 올릴 거라면 아래처럼 한 줄이면 됩니다.

  1. 이름: @는 팀 주소 자체(team1.gdgoc-devfest.org)입니다. api를 넣으면 api.team1.gdgoc-devfest.org가 됩니다.
  2. 서브도메인: 기본은 우리 팀 주소입니다. 추가로 신청한 서브도메인이 있으면 여기서 고릅니다.
  3. 타입: Dokploy 서버로 보낼 때는 CNAME
  4. 값(Target): vps.gdgoc-devfest.org
  5. TTL: auto 그대로 둡니다.
  6. proxy: 처음에는 체크하지 않습니다. 이유는 Cloudflare 프록시에 있습니다.
  7. 추가 버튼
  8. 미리보기: 실제로 만들어질 주소와 연결될 곳입니다. 누르기 전에 꼭 확인하세요.

프론트와 백엔드를 따로 띄울 때의 예시입니다.

만들 주소이름타입값proxy
team1.gdgoc-devfest.org (프론트)@CNAMEvps.gdgoc-devfest.org끔
api.team1.gdgoc-devfest.org (백엔드)apiCNAMEvps.gdgoc-devfest.org끔

CNAME 대신 A 레코드에 IP 103.82.65.75를 넣어도 동작합니다. 다만 서버를 옮기면 직접 고쳐야 하므로 CNAME을 권장합니다. 반영까지는 보통 1~5분 걸립니다. 레코드를 만들기 전에 그 주소로 접속해 봤다면 "없는 주소"라는 답이 캐시되어 최대 30분까지 걸릴 수 있습니다.

개인 VM에 붙이기

팀원이 따로 가진 VM(AWS, GCP, DigitalOcean, 학교 서버 등)에 서비스를 띄웠다면, 공인 IP가 있을 때는 A 레코드 한 줄로 우리 주소를 붙일 수 있습니다. 공인 IP가 없으면 터널을 씁니다.

  1. VM의 공인 IP를 확인합니다. 클라우드 콘솔에 나오거나, VM에서 curl -4 ifconfig.me로 볼 수 있습니다.
  2. DNS 서비스에서 이름 @(또는 api 등), 타입 A, 값에 그 IP를 넣어 추가합니다. proxy는 끈 채로 둡니다.
  3. VM 방화벽(보안 그룹)에서 80, 443 포트를 엽니다.
  4. VM에서 HTTPS를 붙입니다. Caddy를 쓰면 인증서를 알아서 받습니다.
VM (Ubuntu) — Caddy로 HTTPS + 앱 연결
$ sudo apt install -y caddy
$ sudo tee /etc/caddy/Caddyfile <<'EOF'
team1.gdgoc-devfest.org {
    reverse_proxy 127.0.0.1:3000
}
EOF
$ sudo systemctl reload caddy
$ curl -I https://team1.gdgoc-devfest.org
HTTP/2 200

같은 주소를 Dokploy와 개인 VM에 동시에 쓸 수는 없습니다. 레코드 하나는 한 곳만 가리키므로, 프론트는 Dokploy(@), 모델 서버는 개인 VM(ml)처럼 이름을 나눠 쓰세요. VM IP가 바뀌면(재시작 시 바뀌는 클라우드가 있습니다) 레코드 값도 고쳐야 합니다. 고정 IP(Elastic IP, Reserved IP 등)를 쓰거나 API로 자동으로 바꾸게 하면 편합니다.

이름과 값 규칙

항목규칙

쓸 수 있는 글자영문, 숫자, 하이픈(-)만 됩니다. *(와일드카드)와 _는 이름 어디에도 쓸 수 없습니다(_acme-challenge, my_app 등).

한도레코드 + 터널 주소 합쳐서 팀당 10개(기본값). 더 필요하면 운영진에게 요청
요청 속도웹 화면 기준 1분에 전체 120회(그중 추가·수정·삭제는 30회). 넘으면 잠시 뒤 다시 시도하라는 오류가 납니다.

DNS 서비스: 수정과 삭제

  1. Name (주소): 실제 주소입니다. 누르면 새 탭에서 열립니다.
  2. Target (가리키는 곳): 이 주소가 연결된 곳
  3. 수정: 이름, 값, TTL, proxy를 바꿉니다.
  4. 삭제: 확인 창이 뜬 뒤 지워집니다.
  1. 이름 칸. 아래 회색 글씨로 바뀔 주소와 연결될 곳이 바로 보입니다.
  2. 값 칸
  3. 저장: 바뀐 칸만 반영됩니다.
  4. 취소: 바꾸지 않고 돌아갑니다.

DNS 서비스: 서브도메인 추가 신청

팀 주소 아래(api.team1…)는 자유롭게 쓸 수 있으니 대부분 필요 없습니다. 팀 주소와 다른 이름(예: myapp.gdgoc-devfest.org)이 꼭 필요할 때만 신청합니다.

  1. 지금 쓸 수 있는 서브도메인 목록. "기본"이 팀 주소입니다.
  2. 원하는 이름을 영문 소문자, 숫자, 하이픈으로 넣습니다.
  3. 신청: 다른 팀이 이미 쓰고 있거나 예약된 이름이면 거부됩니다.
  4. 추가로 받은 개수 / 최대 5개
  1. 새로 받은 서브도메인. 이제 레코드 추가와 터널의 서브도메인 선택칸에 나옵니다.
  2. 반납: 그 아래 레코드와 터널 주소를 모두 지워야 반납할 수 있습니다.
예약된 이름

www, api, dns, login, admin, official, support 같은 이름과, google, gdgoc, kaist, admin, password가 들어간 이름(google-login 등)은 신청할 수 없습니다. 공식 서비스처럼 보이는 주소를 막기 위해서입니다. 팀 주소 안쪽(api.team1…, www.team1…)은 대부분 자유롭게 쓸 수 있고, 막힌 이름 몇 개만 안 됩니다.

Dokploy: 로그인과 프로젝트

Dokploy 계정은 팀당 하나이고, 대표자 이메일로 초대 메일이 갑니다. 메일의 링크로 비밀번호를 정해 가입한 뒤, 이후에는 platform.gdgoc-devfest.org에서 로그인합니다. 메일이 안 보이면 스팸함을 확인하고, 그래도 없으면 운영진에게 알려 주세요.

  1. Email: 초대받은 대표자 이메일
  2. Password: 가입할 때 정한 비밀번호
  3. Login
  1. 우리 팀 프로젝트 카드. 누르면 프로젝트 안으로 들어갑니다. 다른 팀 프로젝트는 보이지 않거나 열리지 않는 것이 정상입니다.
  2. Create Project: 우리 팀 프로젝트가 없을 때만 씁니다. 버튼도 없으면 운영진에게 알려 주세요.
  1. Name: 팀 ID 그대로 (team1)
  2. Create

프로젝트 하나 안에 프론트엔드, 백엔드, DB처럼 서비스를 여러 개 둘 수 있습니다. 앱은 모두 이 프로젝트 안에 만듭니다.

Dokploy: Application 만들기

앱 하나 = Dokploy의 Application 하나입니다. 프론트와 백엔드를 따로 띄우면 아래를 두 번 합니다. 저장소에 docker-compose.yml이 이미 있으면 Compose로 한 번에 올릴 수도 있습니다.

  1. 우리 팀 프로젝트 안에서 Create Service → Application을 누릅니다.
  2. 이름을 정합니다. 예: web, api. 영문 소문자와 하이픈만 쓰면 헷갈리지 않습니다.

Provider와 Build Type (General 탭)

  1. Provider 탭 중 Git: 공개 저장소 주소로 가져올 때 고릅니다. (탭은 Github, Gitlab, Bitbucket, Gitea, Docker, Git, Drop 순서입니다.) Repository URL에 https://github.com/<계정>/<저장소>.git, Branch에 main을 넣습니다. 앱이 하위 폴더에 있으면 Build Path에 그 폴더(/frontend)를 넣습니다.
  2. Build Type: 아래 표에서 고른 방식에 체크합니다.
  3. Publish Directory: 정적 빌드(Vite, CRA 등)일 때만 dist나 build를 넣습니다. 나머지는 비워 둡니다.
  4. Save: Provider 카드와 Build Type 카드에 각각 있으니, 바꾼 카드의 Save를 누릅니다.

환경 변수 (Environment 탭)

  1. Environment 탭
  2. 입력칸: 한 줄에 KEY=value 하나. 포트를 환경 변수로 받는 앱이면 PORT=3000도 넣습니다. 여러 줄짜리 값(개인 키 등)은 큰따옴표로 감쌉니다.
  3. Save: 누른 뒤 다시 Deploy해야 반영됩니다.
Environment 예시

빌드 시점 변수

NEXT_PUBLIC_, VITE_로 시작하는 값은 빌드할 때 코드에 박힙니다. 바꾸면 Save 후 Deploy(재빌드)를 해야 화면에 반영됩니다.

배포와 로그

  1. 위쪽의 Deploy를 누릅니다.
  2. Deployments 탭에 배포 항목이 하나 생깁니다. 처음 빌드는 몇 분 걸립니다.
  3. 끝나면 Logs 탭에서 컨테이너를 고르고 앱이 에러 없이 떴는지 봅니다.
  1. Deployments 탭
  2. 배포 항목 하나. 상태(Running, Done, Error)와 시각이 나옵니다.
  3. View: 이 배포의 빌드 로그를 엽니다. 실패했으면 맨 아래 줄부터 읽으세요.
  1. Logs 탭
  2. 컨테이너 선택칸: 먼저 골라야 로그가 나옵니다. running이 보이면 앱이 켜져 있는 것입니다.
  3. 로그 영역: 앱이 출력한 내용이 실시간으로 올라옵니다. 오류를 문의할 때 이 부분을 캡처해 주세요.

로그에 Listening on 0.0.0.0:3000이나 Ready 같은 줄이 보이면 성공입니다. 이 시점에는 서버 안에서 앱이 뜬 상태일 뿐, 아직 외부 주소로는 접속되지 않습니다. 다음 단계에서 주소를 붙입니다.

건드리지 말 것

Advanced → Ports는 쓰지 마세요. 서버 포트를 직접 열면 다른 팀과 충돌합니다. 주소 연결은 Domains만으로 충분합니다.

Dokploy: 도메인과 HTTPS

DNS 서비스에서 만든 주소를 Dokploy 앱에 연결하면 인증서까지 자동으로 붙습니다.

  1. Domains 탭
  2. Add Domain: 새 주소 추가 창을 엽니다.
  3. 추가된 도메인 카드: Host, 포트, HTTPS 여부가 보입니다.
  4. Validate DNS: DNS 서비스의 레코드가 이 서버를 제대로 가리키는지 확인합니다. 레코드를 만든 직후라면 몇 분 뒤 다시 눌러 보세요.
  1. Service Name: Compose로 올렸을 때만 나옵니다. 주소를 받을 서비스(예: frontend)를 고릅니다. Application에는 이 칸이 없습니다.
  2. Host: team1.gdgoc-devfest.org (DNS 서비스 레코드와 철자까지 똑같이). 옆의 버튼(무작위 주소 생성)은 쓰지 마세요.
  3. Path: / 그대로
  4. Container Port: 앱이 듣는 포트 (Build Type 표의 마지막 열. 예: 3000, 정적 사이트는 80)
  5. HTTPS: 켭니다. 켜면 아래에 Certificate 칸이 나오고 letsencrypt를 고릅니다.

Internal Path, Strip Path, Custom Entrypoint는 건드리지 않습니다. 저장한 뒤 위쪽 Deploy를 한 번 더 누르고(Application은 저장만으로 반영되기도 하지만, 눌러 두면 확실합니다. Compose는 반드시 눌러야 합니다), 1~2분 뒤 브라우저에서 https://team1.gdgoc-devfest.org를 엽니다.

터미널로 확인
$ curl -I https://team1.gdgoc-devfest.org
HTTP/2 200
content-type: text/html; charset=utf-8
...

Domains를 저장하면 그때 인증서 발급이 시작되고 1~2분 걸립니다. 그 사이 접속하면 잠깐 '안전하지 않음'이 보일 수 있으니 조금 뒤 새로고침하세요. DNS 레코드가 아직 반영되지 않았으면 발급이 실패하므로, DNS 확인이 된 뒤에 Domains를 추가하는 것이 안전합니다.

안 열릴 때 확인 순서
  1. DNS 서비스 레코드 목록에 그 주소가 있고 proxy가 꺼져 있는가 (dig로 확인)
  2. Dokploy Host 칸 철자가 DNS 레코드 주소와 정확히 같은가
  3. Container Port가 앱이 실제로 듣는 포트인가 (Logs 탭의 Listening on …)
  4. 앱이 0.0.0.0에서 듣는가
  5. Domains를 바꾼 뒤 Deploy를 다시 눌렀는가

프론트와 백엔드를 나눌 때

  1. Application을 두 개 만듭니다 (web, api).
  2. DNS 서비스에서 @와 api 두 레코드를 만듭니다.
  3. web의 Domains에는 team1.gdgoc-devfest.org, api의 Domains에는 api.team1.gdgoc-devfest.org를 붙입니다.
  4. 프론트 코드에서 API 주소를 https://api.team1.gdgoc-devfest.org로 씁니다. 브라우저가 부르는 주소이므로 localhost를 쓰면 안 됩니다.
  5. 백엔드 CORS 허용 출처에 https://team1.gdgoc-devfest.org를 넣습니다.

Docker Compose로 올리기

저장소에 이미 docker-compose.yml이 있으면 Create Service → Compose로 여러 서비스를 한 번에 올릴 수 있습니다. 운영진 예시: docker-compose.sample.gdgoc-devfest.org

  1. Git 탭
  2. Repository URL: https://github.com/<계정>/<저장소>.git
  3. Branch: 보통 main
  4. Compose Path: 저장소 안 파일 위치 (보통 ./docker-compose.yml)
  5. Save
  6. Deploy: 저장한 내용으로 배포합니다. Compose는 도메인을 바꿀 때마다 다시 Deploy해야 반영됩니다.
  7. Autodeploy: push할 때마다 자동 배포 (배포한 뒤 참고)

그다음 Domains 탭에서 Add Domain을 누르고, Service Name에서 주소를 받을 서비스를 고른 뒤 Host, Container Port, HTTPS를 위와 같이 채웁니다.

docker-compose.yml 예시
services:
  web:
    build: ./frontend
    expose:
      - "3000"          # ports: 가 아니라 expose:
    environment:
      - NEXT_PUBLIC_API_URL=https://api.team1.gdgoc-devfest.org
  api:
    build: ./backend
    expose:
      - "8080"
    environment:
      - DATABASE_URL=postgresql://app:${DB_PASSWORD}@db:5432/app
    depends_on: [db]
  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=app
      - POSTGRES_PASSWORD=${DB_PASSWORD}
      - POSTGRES_DB=app
    volumes:
      - dbdata:/var/lib/postgresql/data
volumes:
  dbdata:
Compose 규칙
  • ports: 대신 expose:를 씁니다. ports: - "3000:3000"은 서버 포트를 직접 차지해서 다른 팀과 충돌합니다.
  • privileged: true, network_mode: host, /var/run/docker.sock이나 호스트 경로(/, /root 등) 마운트는 쓰지 않습니다. 발견되면 운영진이 서비스를 내립니다.
  • 서비스끼리는 서비스 이름으로 접속합니다 (예: 백엔드에서 db:5432). 도메인을 붙인 서비스는 다른 팀과 같은 공용 네트워크에도 연결되므로, web, api, db 같은 흔한 이름은 다른 팀 컨테이너와 헷갈릴 수 있습니다. team1-web, team1-api, team1-db처럼 팀 ID를 앞에 붙여 주세요. 위 예시도 실제로 쓸 때는 이렇게 바꾸는 것을 권장합니다.
  • 남길 데이터는 이름 있는 볼륨(named volume)에 둡니다.
  • ${DB_PASSWORD} 같은 값은 Compose의 Environment 탭에 넣습니다.

Webhook URL에는 배포를 실행할 수 있는 토큰이 들어 있습니다. 캡처나 단톡방에 그대로 올리지 마세요.

데이터베이스가 필요할 때

프로젝트 안에서 Create Service → Database로 PostgreSQL, MySQL, MongoDB, Redis 등을 만들 수 있습니다. 만든 DB 화면에 나오는 내부 접속 주소(Internal connection URL)를 백엔드 환경 변수(예: DATABASE_URL)에 넣습니다. DB에는 도메인을 붙이지 않고, External Port도 열지 않습니다.

  3. Cloudflare는 0번에서 열린 연결로 요청을 내 컴퓨터의 cloudflared에 넘깁니다.
  4. cloudflared는 주소를 보고 등록된 로컬 포트(localhost:3000 등)로 요청을 넘깁니다. 응답은 같은 길을 거꾸로 돌아갑니다.

3. 내 컴퓨터에서 cloudflared 실행

두 가지 방법 중 하나를 고릅니다. 서버처럼 계속 켜 둘 VM이면 서비스로 등록하고, 노트북에서 데모할 때만 켤 거라면 직접 실행이 편합니다. Windows에서는 관리자 PowerShell을 열고 명령 맨 앞의 sudo를 빼고 실행합니다.

방법 A. 서비스로 등록 (VM, 재부팅해도 자동 연결)
$ sudo cloudflared service install eyJhIjoi...(화면의 토큰)
INF Using Systemd
INF Linux service for cloudflared installed successfully
$ sudo systemctl status cloudflared
● cloudflared.service - cloudflared
     Loaded: loaded (/etc/systemd/system/cloudflared.service; enabled)
     Active: active (running) since ...
     ... INF Registered tunnel connection connIndex=0 ... protocol=quic
     ... INF Registered tunnel connection connIndex=1 ... protocol=quic
방법 B. 직접 실행 (노트북, 창을 닫으면 끊김)
$ cloudflared tunnel run --token eyJhIjoi...(화면의 토큰)
INF Starting tunnel tunnelID=...
INF Registered tunnel connection connIndex=0 ... protocol=quic
INF Registered tunnel connection connIndex=1 ... protocol=quic

Registered tunnel connection이 보이면 Cloudflare와 연결된 것입니다. cloudflared는 QUIC(UDP)이 막힌 네트워크에서 보통 알아서 HTTP/2로 바꿔 연결합니다. 그래도 연결이 안 되면 마지막 수단으로 방법 B에 --protocol http2를 붙여 실행해 보세요.

QUIC이 막힌 네트워크
$ cloudflared tunnel --protocol http2 run --token eyJhIjoi...

4. 주소와 포트 연결

내 컴퓨터에서 앱을 먼저 띄워 둡니다(예: npm start로 3000번). cloudflared는 127.0.0.1(IPv4)로 접속하므로, 앱이 127.0.0.1이나 0.0.0.0에서 들어야 합니다. 일부 Vite·Node 설정은 localhost를 IPv6(::1)로만 열어서 502가 나는데, 이때는 --host 127.0.0.1처럼 주소를 지정하세요. 그다음 DNS 서비스에서 주소를 붙입니다.

  1. 이름: @면 팀 주소 자체, demo면 demo.team1…. 이미 레코드로 쓰고 있는 이름은 쓸 수 없습니다.
  2. 서브도메인
  3. localhost 포트: 내 컴퓨터에서 앱이 듣는 포트. 1024 이상만 됩니다.
  4. 주소 추가
  5. 미리보기: 어떤 주소가 내 컴퓨터의 몇 번 포트로 가는지 보여 줍니다.
  1. Hostname: 공개된 주소. 누르면 새 탭에서 열립니다.
  2. Local port: 연결된 내 컴퓨터의 포트
  3. 삭제: 이 주소의 연결을 끊습니다. 터널 자체와 다른 주소는 그대로 남습니다.

속도와 캐시: 서버가 호주에 있습니다

공용 서버는 호주에 있어서, 한국 사용자가 요청을 한 번 보낼 때마다 국내 서버보다 왕복 시간이 훨씬 깁니다. 작은 API 응답은 크게 티가 나지 않지만, 이미지·동영상·큰 JS 묶음처럼 무거운 파일은 체감이 큽니다. 데모 화면이 느리게 뜨지 않도록 아래를 고려해 주세요.

1. 정적 파일에 캐시 헤더 붙이기

빌드 결과물 중 파일 이름에 해시가 붙은 것(main.3f9a1c.js, _next/static/…)은 내용이 바뀌면 이름도 바뀌므로 오래 캐시해도 안전합니다. HTML은 매번 새로 받게 둡니다.

파일Cache-Control
해시가 붙은 JS, CSS, 폰트, 이미지public, max-age=31536000, immutable
해시 없는 이미지 (/logo.png 등)public, max-age=86400
HTML, API 응답no-cache (또는 헤더 없음)
Express 예시
app.use("/assets", express.static("dist/assets", { maxAge: "1y", immutable: true }));
app.use(express.static("dist", { maxAge: 0 }));
nginx 예시 (정적 사이트를 nginx 컨테이너로 띄울 때)
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location ~* \.(png|jpe?g|webp|avif|gif|svg|ico)$ {
    add_header Cache-Control "public, max-age=86400";
}
location / {
    try_files $uri /index.html;
    add_header Cache-Control "no-cache";
}
gzip on;
gzip_types text/css application/javascript application/json image/svg+xml;

Next.js는 _next/static에 이 헤더를 알아서 붙입니다. public/ 폴더의 큰 이미지만 신경 쓰면 됩니다.

헤더 확인
$ curl -sI https://team1.gdgoc-devfest.org/assets/index-3f9a1c.js | grep -i cache-control
cache-control: public, max-age=31536000, immutable

3. 큰 파일은 공용 서버에서 직접 내보내지 않기

  • 동영상, 수십 MB 넘는 파일, 사용자가 올리는 파일은 Cloudflare R2, Firebase Storage, S3 같은 스토리지에 두고 링크만 씁니다. 동영상은 YouTube 같은 곳에 올리는 편이 가장 빠릅니다.
  • 공용 서버 디스크와 대역폭은 모든 팀이 같이 씁니다. 업로드 파일을 컨테이너 안에 쌓지 마세요.

5. Cloudflare 프록시(캐시) 켜기

레코드의 proxy를 켜면 요청이 Cloudflare를 거쳐 가고, 이미지·JS·CSS 같은 정적 파일은 Cloudflare가 가까운 곳에 캐시해 줍니다. 우리 도메인은 Total TLS가 켜져 있어서 api.team1.gdgoc-devfest.org 같은 깊은 주소도 Cloudflare 인증서가 정상으로 붙습니다.

켜는 순서
  1. 먼저 proxy를 끈 채로 Dokploy 도메인과 HTTPS를 끝내고, https://로 잘 열리는지 확인합니다. Let's Encrypt 첫 인증서는 proxy가 꺼져 있어야 확실하게 발급됩니다.
  2. 그다음 DNS 서비스 레코드 목록에서 수정 → proxy 체크 → 저장합니다.
  3. 몇 분 뒤 응답 헤더에 server: cloudflare가 보이면 Cloudflare를 거치고 있는 것이고, 정적 파일에서 cf-cache-status: HIT가 보이면 캐시에서 나온 것입니다. HTML이나 API는 DYNAMIC으로 나오는 것이 정상입니다.
캐시 확인
$ curl -sI https://team1.gdgoc-devfest.org/logo.png | grep -i -E "server|cf-cache-status"
server: cloudflare
cf-cache-status: HIT      # MISS면 처음 받은 것, 다시 요청하면 HIT
  • Cloudflare는 기본적으로 이미지, JS, CSS처럼 정적 파일 확장자만 캐시하고 HTML과 API 응답은 캐시하지 않습니다. 다만 사람마다 다른 내용을 .png, .js 같은 확장자 주소로 내보낸다면(로그인한 사용자의 프로필 사진 등) 그 응답에는 Cache-Control: private를 붙여 다른 사람에게 캐시된 내용이 가지 않게 하세요.
  • 켠 뒤에 '리디렉션이 너무 많습니다' 오류나 525/526 오류가 나면 바로 proxy를 다시 끄고 운영진에게 알려 주세요.
  • proxy를 켜면 Dokploy의 Validate DNS는 Cloudflare IP를 보게 되어 실패로 표시될 수 있습니다. 사이트가 잘 열리면 무시해도 됩니다.
  • 터널 주소는 처음부터 Cloudflare를 거치므로 따로 켤 필요가 없습니다.

API 키와 curl (DNS 서비스)

여기서 말하는 API 키는 DNS 서비스 전용입니다. Dokploy 계정이나 배포와는 관계없습니다. DNS 서비스 웹 화면에서 하는 일(레코드, 서브도메인, 터널)은 모두 이 키로 API를 불러서도 할 수 있습니다. 스크립트나 CI, 개인 VM에서 DNS를 자동으로 바꾸고 싶을 때만 필요하고, 웹 화면만 쓴다면 몰라도 됩니다.

  1. 지금 계정에 있는 키 목록. 키 앞부분과 상태, 마지막 사용 시각만 보입니다.
  2. 새 키 발급: 기존 키는 모두 폐기되고 새 키가 하나 나옵니다.
  1. 새 키. 기본으로 가려져 있습니다.
  2. 보기 / 가리기
  3. 복사: 가려진 상태에서도 전체 키가 복사됩니다.
  4. 저장했음, 닫기: 닫거나 새로고침하면 다시 볼 수 없습니다. 잃어버리면 새로 발급하면 됩니다.

꼭 지켜야 할 규칙

서버 하나를 모든 팀이 함께 쓰므로, 한 팀의 실수가 다른 팀 데모를 멈출 수 있습니다.

  1. 우리 팀 주소만 씁니다. Dokploy Host 칸에는 DNS 서비스에서 우리 팀이 만든 주소(team1.gdgoc-devfest.org와 그 아래 주소)만 넣습니다. 다른 팀 주소를 넣으면 그 팀 트래픽이 섞입니다.
  2. 서버 포트를 직접 열지 않습니다. Advanced → Ports, Compose의 ports:, DB의 External Port를 쓰지 않습니다.
  3. 권한 높은 설정을 쓰지 않습니다. privileged, network_mode: host, Docker 소켓·호스트 경로 마운트는 금지입니다.
  4. 비밀값은 GitHub에 올리지 않습니다. API 키와 비밀번호는 Dokploy Environment에만 넣습니다.
  5. 자원을 아껴 씁니다. 개발 서버로 띄우지 말고, 안 쓰는 서비스는 Stop하고, 여러 앱을 동시에 빌드하지 않습니다.
  6. Dokploy Domains는 필요한 만큼만 추가합니다. Let's Encrypt 인증서는 gdgoc-devfest.org 전체를 합쳐 주당 50개까지만 발급되므로, Domains를 마구 추가했다 지우면 다른 팀까지 인증서를 못 받습니다.
  7. 계정과 토큰은 팀 안에서만 공유합니다. DNS·Dokploy 비밀번호, API 키, 터널 토큰, Webhook URL을 다른 팀이나 공개된 곳에 올리지 마세요.

운영진은 규칙을 어긴 서비스를 사전 안내 없이 멈출 수 있습니다.
